## 2. Root cause

`BookingRepository.findById()` (`backend/src/modules/booking/infrastructure/repositories/booking.repository.ts`,
originally lines 124-125) selected `r.name AS resource_name` and `br.name AS branch_name` using **INNER JOINs**:

```sql
FROM bookings b
JOIN resources r ON r.id = b.resource_id
JOIN branches  br ON br.id = b.branch_id
WHERE b.id = ?
```

A booking row that exists and is readable can still fail to resolve when:

1. `bookings.branch_id IS NULL` (allowed by `fk_booking_branch ... ON DELETE SET NULL`), or
2. `bookings.resource_id` points at a `resources` row that no longer exists (`bookings.resource_id` has **no FK**).

In both cases the INNER JOIN produces no row, `findById()` returns `null`, and every caller treats the booking as
non-existent. In the auto-complete worker this produced a repeated level-50 `NotFoundError: Booking not found`
(twice per run, every 5 minutes) and prevented the booking from ever leaving `confirmed`.

`[CONFIRMED]` by: read-only DB inspection of `bookings`/`information_schema.referential_constraints`, the compiled
artifact, and the pre-deployment container logs.
